# 大模型 App 抓包开发经验

记录日期：2026-10-17（Asia/Shanghai）。本文来自本项目的真机实验、导出证据和代码验证，不是各平台协议的官方说明。元宝结论限定为 Android 版 2.88.0 的本地测试环境；豆包、Kimi、千问、文心一言尚未完成同等验证。

模块扩展见 [架构说明](architecture.md)，结果读取见 [ADB 接口 v1](automation-v1.md)。本文侧重如何定位问题、验证结果和避免重复走弯路。

## 1. 先定义成功，再开始调试

一次实时回答采集成功，需要同时满足：

1. 抓包仍在运行，目标应用正常完成逐步回复，不能先停止 VPN 再判断成功。
2. 在本次实时请求中找到准确的测试问题或唯一标记，并能对应到同一响应。
3. 确认真实协议。SSE 应有 HTTP 响应及 `text/event-stream`，并能按事件语法解析正文。
4. 请求和响应生命周期完整，正文未截断、未处于接收中，无传输或远端错误。
5. 拼接规则符合该协议，最终文本与手机显示或独立取得的最终回答核对一致。

单独出现 HTTP 200、创建会话成功、历史接口里的完整答案、加密 TCP/QUIC 数据或打字动画，都不足以证明已取得实时 SSE。历史详情可以用于独立核验，但不能替代本次实时响应作为答案来源。

## 3. 按层排查，避免把所有失败归结为证书固定

建议依次区分：VPN 转发 → 目标应用到本机代理的 TLS → 代理到服务器的 TLS → TLS 内部协议 → HTTP 实体解码 → SSE → 平台语义 → 任务关联。

| 现象 | 优先确认 | 不能直接得出的结论 |
| --- | --- | --- |
| 关闭 HTTPS 解密时能回复，开启后失败 | 两轮是否保持其他条件一致；失败发生在哪一侧 TLS、哪个阶段 | 一定是 pinning，或者一定是目标 App 拒绝 CA |
| 部分普通接口已解密，但聊天仍失败 | 聊天是否使用不同域名、原生库或独立信任库 | 整个 App 都已经信任抓包 CA |
| `ClosedChannelException` 或空错误消息 | 首次失败、异常类型及 cause 链、握手阶段、连接时间 | 连接关闭本身就是根因 |
| 目标应用侧 TLS 已成功，上游提示 SAN 不匹配 | 上游连接地址、SNI、证书校验名与证书 SAN | 需要关闭服务器证书校验 |
| TLS 已解密却没有 HTTP | 明文是否为原生二进制网关协议，ALPN/首字节是否支持 HTTP 判断 | 所有 TLS 都应该交给 HTTP 解码器 |
| 有 UDP 443 或 Google QUIC 版本头 | 本轮开关、实际目的端、协议版本、是否另有网络栈 | 已能解密 QUIC，或禁用一处策略就能关闭全部 QUIC |
| 有 SSE 但只有半段正文 | 是否仍在接收、gzip 前缀、配额、连接中断及结束事件 | HTTP 200 或已有部分文字就代表完成 |

在只有症状而没有新证据时，不要让用户反复发送相同问题、固定等待很长时间。下一轮测试应能区分一个明确假设。

## 4. 证书信任与 TLS：本次最关键的两次定位

### Java 与原生网络栈可能使用不同信任库

本次仅配置 Android 用户 CA、修改 Java 层信任配置、向 APK 自带 PEM 追加 CA，均未单独解决聊天失败。静态调查发现 Java 客户端读取独立 PEM，而原生聊天路径使用另一套网络实现。

继续跟踪 `libdtmp.so` 的原生网络导入，发现 `CreateSSEClient` 等入口由 `libwemeet_base.so` 提供，并定位到其实际初始化 TLS 根证书集合的路径。在本地测试版本中保留原有两组根证书，仅额外信任既有抓包 CA，之后才观察到目标应用侧握手成功。

可复用的经验是：追踪实际网络调用与证书加载链。看到函数名含 `Verify`、发现一段 PEM 或搜到 `disable_ssl_pinning` 字符串，都不足以证明找到了本次失败的校验路径。嵌入的 DER 也可能用于公共证书压缩等其他用途，不能直接当作信任根集合。

### 客户端信任代理，不等于代理已能连接服务器

目标应用侧 TLS 修复后，新的失败信息是上游证书域名不匹配。独立验证显示，同一服务器按 IP 校验失败，按 `api.yuanbao.tencent.com` 校验通过。此前的客户端信任问题与此时的上游身份问题是两件事。

因此本项目增加 `tlsHostOverrides`：保持网络连接地址不变，仅明确上游 SNI 和校验域名，并保留系统信任链及主机名校验。配置形式为 `原主机=证书域名`，具体源 IP 应在当前实验中核实，不把某次解析出的地址写进平台适配器。

诊断时须同时记录两侧 TLS 的成功/失败。禁止把“目标应用侧握手未完成”统一写成“目标应用拒绝证书”；也不要用 trust-all 掩盖尚未定位的问题。

## 5. 已经走过但不能作为通用解法的尝试

| 尝试 | 本次观察 | 后续做法 |
| --- | --- | --- |
| 阻止 UDP 443，期待回退 TCP | 有过等待无回复、停止抓包后才看到回复的轮次 | 作为可选实验，不能承诺 App 支持回退；成功实验未开启此开关 |
| 修改三处原生 HTTP QUIC 策略 | 后续仍能观察到另一条网络路径的 Q043 流量 | 不把局部策略修改说成关闭全部 QUIC，先确认各网络栈 |
| Java CA 配置或只追加 APK PEM | 普通接口可读，聊天仍失败 | 继续确认聊天实际使用的原生信任库 |
| 仅导出 HTTP 条目 | 握手阶段失败的连接没有 HTTP 请求，关键原因缺失 | HAR 额外保留全量连接与失败信息 |
| 用历史详情中的答案证明实时成功 | 能拿到完整答案，但并非实时事件流 | 历史用于核对，实时证据单独保存 |
| 多项修改叠加、开关记录不明确 | 部分失败轮次无法构成严格单变量对照 | 给每轮实验记录版本、摘要、开关、时间和用户观察，不倒推因果 |

这些失败记录也有价值：保存“已修改且构建成功，但真机验证失败”的状态，避免下次将构建报告误当作可用方案。

## 6. SSE 与流式采集的实现经验

- 网络包、HTTP chunk、gzip 输出块、UTF-8 字符和 SSE 事件不是同一种分界。不能逐 TCP 包解析 JSON，也不能逐字节块独立解码 UTF-8 后直接拼接。
- SSE 用空行分隔事件，支持 CR/LF/CRLF、多行 `data`、`event`、`id` 和注释。未收到分隔空行的尾部不能当作已完成事件。
- 不等待连接关闭才展示正文。采集约每秒发布可读快照，并明确 `inProgress`；快照读取不得阻塞网络转发线程。
- SSE 可以合法地长时间无输出，不能照搬普通 HTTP 读空闲超时。连接结束与应用层 `[DONE]` 也应分别核查。
- gzip 在接收中可能只有前缀，应保留“正在等待/接收中”的状态；最终实体解压失败则不能报告完整。
- TLS 握手后再识别 HTTP 或原生明文流。协议探测需要有超时、有限缓存和关闭清理；本项目目前有 1.5 秒探测窗口及有界字节暂存，这些是实现约束，不是目标平台的协议保证。
- 超过配额继续转发，但必须标记正文截断。采集成功转发与证据完整是不同状态，结果层需要检查后者。
- UI 只显示最近 200 条请求、最近 500 个 SSE 事件。导出与回答重建必须读取完整保存的数据，不能复用 UI 列表窗口；本项目已有超过窗口大小的测试。
- 导出中保留原始内容和接收状态。HAR 的 `log._connections`、`log._transportStreams` 是本工具扩展，包含未产生 HTTP 的连接与原始流；不要伪造成标准 HTTP 条目。

关键代码可从这些位置进入：

| 层次 | 代码 |
| --- | --- |
| 两侧 TLS、协议探测 | `capture/.../proxy/LocalProxy.kt`、`capture/.../crypto/LocalCertificateAuthority.kt` |
| 连接错误与生命周期 | `capture/.../proxy/ProxyFailureDescription.kt`、`capture/.../engine/ConnectionRegistry.kt` |
| SSE 快照与转发 | `capture/.../engine/TrafficRecorder.kt`、`capture/.../proxy/ExchangeBridge.kt` |
| 正文解码、限额及导出 | `data/.../BodyDecoder.kt`、`FileBodyStore.kt`、`TrafficExporter.kt` |
| 事件语法与平台语义 | `core/.../ServerSentEvents.kt`、`llm/.../YuanbaoDecoder.kt`、`AnswerReader.kt` |

表中 `...` 省略各模块的 `src/main/kotlin/com/packetcapture/{模块名}` 包路径。

## 7. 元宝事件解析与核对细节

本次样本的请求 `prompt` 与 `type=text` 事件中的字符串 `msg` 分别对应问题和答案增量。第一个文本事件可能只有 `type` 没有 `msg`，不应因此添加空占位文字。其他 `speech_type`、`step`、提示及控制帧不拼进答案。

结束检查同时使用 `[DONE]`、`meta.stopReason=stop`、`modelErrorCode=0` 和传输状态。即使 HTTP 200 且有 `[DONE]`，远端错误、登录要求、截断或未完成生命周期也不能算成功。新事件类型需要重新验证，不可静默略过后继续报告完成。

引用来源从 `searchGuid.docs` 的有效 HTTP(S) URL、标题和索引取得，与正文分开。正文中的 `[citation:...]`、`[](@mark_underline=...)` 等标记保留为原始答案的一部分；后续若需要可读清洗，应派生单独展示字段，不能覆盖用于证据核对的原文。当前来源列表不承诺逐句对应或穷尽全部引用。

这次回放还遇到两个文本核对细节：

- Kotlin `String.length` 计算 UTF-16 code unit，Python 的常用字符串长度按 Unicode 码点；包含非 BMP 字符时数字可能不同。本样本为 1,394 个 UTF-16 code unit、1,393 个码点，不能因此判断少/多了一个字。
- Windows 保存的 Markdown 可能使用 CRLF，SSE 拼接文本包含 LF。比较可读文件时可统一换行，但原始报文继续原样保存；不能通过删除任意空白或引用标记让差异消失。

其他平台可能下发累积快照、局部替换、分开的推理和答案，不能直接沿用元宝的追加策略。适配前必须通过真实样本确定语义。

## 8. 真机、构建和实验记录

### 每轮最少记录

记录设备/系统、包名/版本、已安装 APK 摘要与 signer、抓包 App 版本、目标应用集合、HTTPS/UDP443/代理/TLS 映射、开始与发送时间、问题标记、用户观察、会话/请求 ID、正文截断与结束状态、原始证据路径。

尽量只改变一个变量。记录以手机实际安装版本和界面状态为准；不要根据 APK 文件名推测已经安装，也不要混用昨日失败结论和今日成功证据。

问题标记用于人工核查；接入任务系统后仍需持久化 `taskId/attemptId`、设备时间起点、`sessionId/exchangeId`。多个相同问题命中应报告歧义，不能擅自选最新答案。超时后先继续收集已发请求，不自动再提问。

### Windows 与 Android 操作

- 本机使用 PowerShell 7（`pwsh`），JDK 21，SDK/NDK/CMake 版本见 README。用 `Join-Path` 组合路径，显式使用设备 serial，避免多设备操作串线。
- 保留已安装测试版本使用的 signer，覆盖更新不要卸载、清数据或重建 CA。CA 更换会破坏已配置的目标应用信任，清数据还会丢失历史证据。
- Release 构建默认未签名，不能直接用 debug 包覆盖现有不同签名的安装。修改目标应用签名也可能影响微信/QQ等第三方授权登录，本次曾出现签名不一致；不要通过反复重试授权登录排查网络问题。
- 签名密码用本地密码文件传给工具，不输出到日志；已有签名文件只保存在忽略目录。二进制实验需要锁定原始摘要、核对实际差异、签名、对齐及可覆盖回退条件，虚拟地址不能直接当文件偏移使用。
- 本次实体手机可用，模拟器曾在登录环节崩溃。不要把模拟器结果等同于真机结果。
- 输入法可能重排快速 ADB 输入；发送前回读 UI 核对问题。键盘返回键也可能触发页面返回，优先确认实际键盘/页面状态，不硬编码坐标到跨设备自动化。
- 运行中也能从历史会话导出 HAR，无需先停止抓包；导出后检查正文状态，运行中导出不意味着每条记录都已完成。

常用只读准备命令（PowerShell 7）：

```powershell
$adbPath = Join-Path $env:ANDROID_HOME 'platform-tools/adb.exe'
& $adbPath devices -l
$deviceSerial = 'YOUR_DEVICE_SERIAL'
$targetPackage = 'com.tencent.hunyuan.app.chat'
& $adbPath -s $deviceSerial shell dumpsys package $targetPackage |
    Select-String -Pattern 'versionName=|versionCode='
```

测试与构建命令见 [接口验证说明](automation-v1.md#验证)。单元测试、APK 构建、实际安装、设备操作和端到端实时回答是不同验证层次，各自记录通过与未执行状态。当前 1.1.0 的解析回放和构建通过，但新增设置 UI 与 ADB 接口未做真机验证。

## 9. 下一个平台的最短验证流程

1. 核实当前包名、版本及渠道；先做抓包透传基线，确认网络没有被工具本身破坏。
2. 开启 HTTPS 解密，按连接阶段定位信任、上游身份或传输问题；每轮保留开关状态和证据。
3. 找到包含本次问题的实时请求，判断 SSE、WebSocket、原生流或其他协议；未取得明文时不写“已支持”。
4. 保存原始请求/响应和完成状态，分析增量、推理、来源、错误与结束语义。
5. 新增平台解码器及合成/脱敏测试，覆盖正常、异常、截断、重复候选和协议变更。
6. 真机正常回复、完整明文、结果核对都通过后，再提升平台支持状态；在文档记录验证版本和前提。

保留实验原始资料在 `artifacts/`；将可复用经验、合成测试和代码提交 Git。公共文档不附登录凭据、私人对话、设备标识或测试签名材料。
